# 写作规范

这份文档是给**未来的自己和自动化脚本**看的。新文章按这里来，风格才统一。

## 一、文件怎么命名

```
content/posts/YYYY-MM-DD-标题.md
```

例：`content/posts/2026-09-15-建站日志.md`

- 日期用发文章的日期，**不要**用写作日期
- 标题里的空格换成连字符；中文直接留着，不必硬转拼音
- 不要用 `/ \ : * ? " < > |` 这些字符

用脚本创建最省事：

```bash
./scripts/new-post.sh "文章标题"            # 通用模板
./scripts/new-post.sh "论文复现：XXX" research  # 论文复现模板
```

## 二、frontmatter 字段

```yaml
---
title: "文章标题"                    # 必填
date: 2026-09-15T20:30:00+08:00     # 必填，注意带时区
draft: true                          # 必填。发布前改成 false
author: "你的署名"                 # 必填。不想署真名就写昵称
tags: ["Hugo", "GitHub Pages"]       # 建议 2–5 个
categories: ["工程"]                  # 只从下面的固定集合里选一个
description: "一句话摘要"             # 会用于 <meta description> 和列表页，**认真写**
summary: ""                          # 留空则用 description
showToc: true                        # 长文建议开
TocOpen: true                        # 小节多的话建议默认展开
comments: false
---
```

### categories 固定集合

只在这四个里选，**不要随手新增**（否则归档页会碎成一堆只有一个条目的分类）：

| 分类 | 放什么 |
|---|---|
| `工程` | 环境、脚本、部署、工具链 |
| `论文复现` | 复现某篇工作的完整记录 |
| `建模` | 推导、公式、假设分析 |
| `随笔` | 说明、计划、反思 |

### tags 怎么打

- **技术栈**：`Hugo`、`Python`、`CUDA`、`Hugo`…
- **研究方向**：`多无人机`、`空域调度`、`冲突消解`…
- **动作**：`复现`、`踩坑`、`实测`

tags 可以随时间自由生长，但**同一个概念只用一个写法**（别一会儿 `无人机` 一会儿 `UAV`）。要改名就全局搜一遍一起改。

## 三、正文怎么写

### 结构

长文用二级标题分节，**不要超过三级**。开头三行内说清"这篇解决什么问题"。

### 结论先行

技术笔记最忌讳吊胃口。第一段就给结论，后面再讲过程：

```markdown
结论先行：**`raw.githubusercontent.com` 在两边都不通。**
```

### 代码块

- **必须标语言**（渲染才有着色）：```` ```bash ````、```` ```python ````、```` ```toml ````
- 长输出截断，只留关键几行，别整段贴日志
- 命令和输出分开 —— 别把 `$` 提示符和结果混在一个块里

### 表格

对比类信息一律用表格，别写成流水句：

```markdown
| 入口 | 结果 | 用途 |
|---|---|---|
| `api.github.com` | ✅ 200 | 读文件 |
```

### 文献引用

**这是硬要求。**

- 正文里提到某篇工作，**必须带年份和可核实出处**：
  - ✅ 「Chung & Jang, *Applied Soft Computing* 161 (2024) 111725」
  - ❌ 「有篇论文提出过」
- 有 DOI / 会议页链接就挂上
- **预印本、学位论文、专利不作正式引用**，需要提就明确标注类型
- **没核实的写「待复核」**，不要写成结论

### 不确定的事怎么写

有一说一，用这三个词区分：

| 情况 | 写法 |
|---|---|
| 跑过、有数据 | 直接陈述 + 给数据 |
| 查过资料、有出处 | 「据 X（2024）…」 |
| 只是推测 | 「**待核实**：我怀疑是…」 |

**不要用「我觉得应该没问题」这种句子。** 要么验证，要么标成待核实。

## 四、发布流程

```bash
./scripts/publish.sh "post: 文章标题"
```

脚本会：拉远端（`--rebase`）→ 提交 → 推送 → 触发 Actions 构建 → 约 40 秒后上线。

### 三种修改方式，按改动大小选

| 场景 | 怎么做 |
|---|---|
| 改错别字、调一两句 | **GitHub 网页**直接编辑文件 → Commit。最快 |
| 写新文章 / 大改 | 服务器或本机编辑 → `./scripts/publish.sh` |
| 只想看效果不想提交 | `./scripts/preview.sh`（需要本机装 Hugo） |

### 提交信息约定

```
post: 新建站日志          # 新文章
edit: 修正复现结果表格     # 改已有文章
site: 调整导航栏           # 改站点配置/主题
```

## 五、给自动化脚本的约定

如果由脚本生成初稿：

1. 文件写到 `content/posts/`，命名同上
2. **`draft: true`** —— 生成的稿子一律先当草稿
3. frontmatter 里加 `generated: true`，方便日后筛出来复核
4. 正文开头加一行：`<!-- 初稿由脚本生成，发布日期：YYYY-MM-DD，需人工核对文献与数据 -->`
5. 涉及具体数字和文献的地方，**宁可留空写「待补」，也不要编**

## 六、几个容易忘的点

- 图片放 `static/images/`，正文里写 `/images/xxx.png`（**注意开头的斜杠**，否则子路径下会 404）
- 中文标点用全角，代码和路径用半角
- 文章之间的链接用相对路径 `/posts/xxx/`，别硬编码 `https://huoguo565656.github.io/...`，将来换域名会全废
